# 카드 상세 로어(상징·이야기·대응) 설계 — 2026-07-24

## 목적

카드 상세 화면(`/collection/[deckId]/[slug]`)은 지금 해석 2문단이 전부라, 도감(소유 기반 갤러리)의 콘텐츠 가치가 얇다. 덱 소유를 파는 비즈니스 모델에서 상세 화면의 풍부함이 곧 상품 가치다. 2026-07-22 세션 #12("카드 아트 상세에서 흥미를 이끌 정보를 웹 서치로 보강")의 이행이다.

## 확정 요구사항

- **콘텐츠 축 3개**: 상징 해부, 역사·문화 이야기, 점성술·수비학 대응. 텍스트만(이미지 없음).
- **범위**: 78장 전부. RWS(라이더-웨이트) 기준 공통 1벌 — 클래식·월하비원·K-POP 뮤즈버스 3개 덱 상세에 동일 노출.
- **마이너 아르카나는 결 다르게**: 메이저=카드 개별 이야기, 마이너=수트·숫자의 흐름 속 이 카드의 자리 + 고유 포인트. 모든 카드가 같은 섹션 구조를 가진다.
- **UI**: 해석 본문 아래 접힘 섹션 3개(기존 "영어 원문 보기" `<details>` 패턴).
- **면책 안내**: 프리미엄 덱에서만, 접힘 섹션 위에 뮤트 캡션.
- **검수 주체**: 톤·정확성 검수는 Opus 4.8 서브에이전트가 한다(메인 세션 Fable은 오케스트레이션·최종 확인만).

## 1. 데이터 모델

```ts
// src/data/lore/types.ts
export type LoreSymbol = { name: string; meaning: string }; // "흰 장미" / 1~2문장

export type CardLore = {
  symbols: LoreSymbol[]; // 3~5개
  story: string;         // 1~2문단, \n\n 구분
  astrology?: string;    // 카드 고유 대응만: 메이저=행성·별자리, 마이너 2~10=데칸.
                         // 에이스·코트는 생략(황금새벽회 구간 표기는 일반 사용자에게 과함)
};
```

- 데이터 파일 5개 분할(기존 `ko-focus-*.ts` 패턴): `src/data/lore/major.ts`(22장), `wands.ts` `cups.ts` `swords.ts` `pentacles.ts`(각 14장). slug 키는 `ko.ts`와 동일.
- **규칙 산출(데이터로 쓰지 않음)**: 수트→원소 매핑(완드=불, 컵=물, 소드=공기, 펜타클=흙), 숫자→수비학 의미 매핑(에이스=시작 … 10=완성, 코트는 수비학 없음). 메이저의 원소·행성·별자리는 규칙이 없으므로 카드별 데이터 — astrology 문자열에 함께 표기한다(예: 바보 = "천왕성 · 공기").
- 렌더 진입점은 `cardLore(slug)` 헬퍼 하나: 5개 레코드를 합치고 규칙 산출값(원소·수비학)과 카드 고유값(astrology)을 묶어 완성된 대응 정보를 돌려준다.

## 2. UI — 카드 상세 화면

본문 구조(위에서 아래로):

```
해석 본문 (기존)
영어 원문 보기 (기존 토글)
[프리미엄 덱만] 안내 캡션
▸ 카드 속 상징들
▸ 카드 이야기
▸ 전통 대응
수집 이력 (기존 CollectHistory)
이전/다음 카드 (기존 CollectedCardNav)
```

- 새 컴포넌트 `LoreSections` — **서버 컴포넌트**(데이터 정적, 클라이언트 상태 불필요). `<details>/<summary>` 3개.
- **카드 속 상징들**: 상징 이름 소제목 + 의미 1~2문장 리스트.
- **카드 이야기**: 해석 본문과 같은 산문 스타일(font-serif) 1~2문단.
- **전통 대응**: 라벨-값 담백한 인라인 나열(원소 · 불 / 수비학 · 시작 / 점성술 · 천왕성). 없는 값은 줄 생략.
- **안내 캡션**(프리미엄 덱 2종에서만, 클래식은 자명하므로 숨김 — 페이지가 `deckId`를 이미 안다):
  > 아래 이야기는 클래식 덱(라이더-웨이트)의 그림을 기준으로 합니다. 프리미엄 덱은 같은 카드를 저마다의 시선으로 새로 그린 것이라, 그림 속 표현은 다를 수 있습니다.
  - "면책"이 아니라 안내로 읽히게 — 프리미엄 덱을 "저마다의 시선"으로 표현해 상품 가치를 깎지 않는다. 문구는 구현 시 다듬을 수 있다.
- 상징 서술은 아트 중립으로: "그림 속 절벽" 대신 "절벽 끝의 발걸음" — 프리미엄 아트와의 직접 충돌을 피한다.

## 3. 콘텐츠 생산 파이프라인

**소싱 원칙**(기존 `reversed.ts` 주석 패턴 계승 — lore 파일 상단에 근거 주석 명시):

- 상징 해부: Waite, *The Pictorial Key to the Tarot*(1911, 퍼블릭 도메인)의 도상 서술 + 웹서치 교차 확인. 문장을 그대로 옮기지 않고 뜻만 가져와 앱의 목소리로 새로 쓴다.
- 역사·문화: 웹서치 리서치(비스콘티-스포르차, 마르세유→RWS 계보, 카드별 일화). 확인 안 되는 속설은 "~라는 이야기가 전해집니다"로 명시적으로 구분한다.
- 점성술 대응: 황금새벽회(Golden Dawn) 표준 대응표 — 확립된 체계라 정오 검증이 명확하다.

**작업 분배**(CLAUDE.md 어드바이저/워커 모델):

1. **초안 작성**: 워커 5개 병렬(메이저 22장 / 수트별 14장 × 4) — 웹서치 리서치 후 `lore/*.ts` 각 1파일 작성.
2. **톤·정확성 검수**: **Opus 4.8 서브에이전트**(사용자 지정 — Fable이 하지 않는다). 기준:
   - 해석 감사 기준(`docs/tarot-interpretation-audit-2026-07-23.json`)의 겁주지 않는 성찰적 톤
   - Pictorial Key·황금새벽회 대응 대비 사실 정확성
   - 78장 간 구성 일관성
3. **최종 확인**: 어드바이저가 diff·테스트 직접 검증 후 커밋.

## 4. 테스트

기존 `decks.test.ts` 스타일 단위 테스트:

- 78개 slug 전수 존재(카드 목록 ↔ lore 레코드 합집합 대조)
- symbols 3~5개, 모든 필드 빈 문자열 없음
- story 문단 수 1~2(\n\n 기준)
- 규칙 매핑 함수(수트→원소, 숫자→수비학) 단위 테스트

실행: `./node_modules/.bin/vitest run` / `./node_modules/.bin/tsc --noEmit` (dev 서버 떠 있을 때 `npm run build` 금지 — next-dev-cache-traps 메모 참조).
