# P1.1 마무리: 변경 전파 · 저널 동기화 · 로그아웃 설계

- 작성일: 2026-07-22
- 브랜치: `redesign/arcana`
- 상위 문서: [`2026-07-19-arcana-ia-design.md`](2026-07-19-arcana-ia-design.md) (D1 게스트 우선), [`2026-07-19-p1.0-supabase-foundation.md`](../plans/2026-07-19-p1.0-supabase-foundation.md)
- 범위: `7e6af41`(P1.1 auth 골격)이 남긴 follow-up 3건 — **push-on-mutation**, **저널 서버 동기화**, **로그인 병합 후 UI 갱신**.

## 1. 배경

P1.0에서 스키마·클라이언트·`mergeStores`·`pullRemoteStore`/`pushLocalStore`를, P1.1에서 세션·OAuth 콜백·`syncOnLogin`을 만들었다. 그러나 실제로 데이터가 흐르지 않는다:

1. **`pushLocalStore`를 아무도 호출하지 않는다.** `syncOnLogin` 안에서 단 한 번뿐이라, 로그인 이후에 뽑은 리딩은 서버에 영영 올라가지 않는다.
2. **저널은 원격 경로 자체가 없다.** `journal_entries` 테이블은 있지만 `pullRemoteJournal`/`pushLocalJournal`이 없다.
3. **`useArcanaStore`는 마운트 시 1회만 읽는다.** `refresh`를 호출하는 곳이 없어, `AccountCard`가 로그인 병합을 끝내도 열려 있는 화면은 옛 값을 계속 보여준다.

세 결손은 개별 버그가 아니라 **"로컬 저장이 바뀌었다"는 사실을 전파할 통로가 없다**는 하나의 결손이다. 본 설계는 그 통로를 만들고 세 문제를 동시에 닫는다.

## 2. 확정된 설계 결정 (Decision Log)

| # | 결정 | 값 |
|---|---|---|
| S1 | 동기화 목표 | **계정 백업.** 한 번에 한 기기를 쓴다고 가정한다. 멀티 디바이스 동시 사용(실시간 구독·포그라운드 재동기화)은 범위 밖 |
| S2 | 로컬 권위 | 로그인 이후 **로컬이 권위**다. 서버는 복구용 사본. pull은 로그인 시점 1회 |
| S3 | 저널 충돌 | 같은 날짜가 양쪽에 있으면 **`updatedAt`이 최신인 쪽**(LWW) |
| S4 | 저널 삭제 | 톰스톤을 두지 않는다. push가 **로컬에 없는 서버 행을 삭제**해 삭제를 전파한다 (S2의 귀결) |
| S5 | 로그아웃 | 대기 중 push를 flush한 뒤 **로컬 저장소를 비운다**. 공용 기기에서 남의 일기가 보이거나 다음 계정에 섞이는 사고를 막는다 |
| S6 | 실패 처리 | 재시도 큐를 두지 않는다. push는 **전체 스토어 멱등 upsert**라 다음 push가 밀린 것까지 복구한다. MY 계정 카드에 상태 한 줄만 노출 |
| S7 | 전파 방식 | 저장 함수가 **키 있는 변경 이벤트**를 emit하고, 화면 훅과 `SyncBridge`가 각각 구독한다. 호출부에서 push를 직접 부르지 않는다 |
| S8 | 게스트 불변 | Supabase env가 없거나 세션이 없으면 `SyncBridge`는 즉시 빠져나간다. 게스트 경로에 네트워크가 끼어들지 않는다 |

### S7을 택한 이유

대안은 호출부에서 `recordReading()` 뒤에 push를 명시 호출하는 것이었다. diff는 작지만 (a) 새 저장 경로가 생길 때 빠뜨리면 **조용히 백업이 새고**, (b) UI 갱신은 여전히 별도 메커니즘이 필요해 결국 두 갈래가 된다. 이벤트 방식은 저장하면 반드시 흐르므로 P2에서 사주 리딩 저장 경로가 추가돼도 누락이 구조적으로 불가능하다.

## 3. 아키텍처

새로 생기는 조각은 3개다.

```
src/lib/local-events.ts     변경 이벤트 채널 (~25줄, 의존성 없음)
src/components/SyncBridge   layout에 1개. 세션 관찰 + 디바운스 push + 상태 노출
src/lib/sync/journal-remote.ts  저널 pull/push
```

의존 방향은 한 방향으로 유지한다:

```
store.ts / journal.ts  ──emit──▶  local-events.ts  ◀──subscribe──  useArcanaStore / useJournal
                                        ▲
                                        └──subscribe──  SyncBridge ──▶ sync/*  ──▶ supabase/*
```

`store.ts`·`journal.ts`는 **Supabase를 import하지 않는다.** 로컬 우선 원칙(P1.0 Global Constraints)이 그대로 유지되고, 두 파일의 유닛테스트도 네트워크와 무관하게 남는다.

### 3.1 `local-events.ts`

```ts
export type LocalChannel = "store" | "journal";
export function subscribeLocal(ch: LocalChannel, fn: () => void): () => void;
export function notifyLocal(ch: LocalChannel): void;
```

채널을 나누는 이유는 일기 저장이 도감 화면을 리렌더시키지 않게 하기 위함이다. SSR 안전(모듈 스코프 `Map`, 브라우저 전용 API 없음).

### 3.2 emit 지점

`store.ts`의 `saveStore`, `journal.ts`의 `saveJournal` **내부** 끝에서 emit한다. 두 함수는 이미 모든 쓰기(`recordReading`, `setLocalStore`, `setEntry`)가 지나는 단일 통로이므로, 여기 한 곳만 잡으면 새는 경로가 없다.

### 3.3 구독 지점

- `useArcanaStore` / `useJournal`: 마운트 시 해당 채널을 구독해 `refresh`를 건다. 기존 `refresh` 반환값은 유지(호환).
- `SyncBridge`: 두 채널을 모두 구독한다.

### 3.4 `SyncBridge`

`layout.tsx`의 `<body>`에 `<NoPinchZoom />` 옆에 놓는 클라이언트 컴포넌트. UI를 렌더하지 않는다(`null`).

책임:
1. `useSession()`으로 `user: null → {id}` 전이를 감지해 `syncOnLogin(id)` + `syncJournalOnLogin(id)` 실행. (지금 `AccountCard`가 갖고 있는 이 로직을 여기로 **옮긴다** — MY 화면을 열어야만 병합되는 현재 동작은 버그다.)
2. 변경 이벤트를 받아 **2초 디바운스** 후 로그인 상태면 push.
3. `window` `online` 이벤트에 push를 건다(오프라인 복귀 복구).
4. 동기화 상태를 노출한다.

## 4. 데이터 흐름 시나리오

### 게스트 (env 없음 또는 미로그인)
`recordReading()` → `saveStore()` → `notifyLocal("store")` → 화면 갱신. `SyncBridge`는 세션이 없어 무시. **현행과 동일하며 네트워크 호출이 없다.**

### 첫 로그인 (게스트 기록 보유)
```
OAuth → /auth/callback → 세션 확립
  → SyncBridge가 전이 감지
  → syncOnLogin(id):        pull → mergeStores → setLocalStore → push
  → syncJournalOnLogin(id): pullRemoteJournal → mergeJournals(LWW) → setLocalJournal → push
       ↑ setLocalStore/setLocalJournal이 notify를 쏘므로 열려 있는 모든 화면이 병합 결과로 갱신
```

### 로그인 상태에서 저장
`recordReading()` / `setEntry()` → notify → ①화면 갱신 ②`SyncBridge` 디바운스 2초 → push.

### 오프라인·실패
push 실패 → 상태 `error` → MY에 `동기화 대기 중`. 로컬은 이미 저장돼 앱은 정상 동작. `online` 복귀 또는 다음 저장 시 전체 멱등 upsert로 밀린 분까지 복구.

### 로그아웃
```
signOutAndClear():
  대기 중 push flush(await) → localStorage 비움 → notify → 화면 리셋 → supabase.auth.signOut()
```
재로그인 시 pull로 복구된다.

## 5. 저널 원격 계층

`journal_entries` 스키마: `(user_id, entry_date)` PK, `body`, `updated_at`.

```ts
// src/lib/sync/merge.ts (순수 · 테스트 대상)
export function mergeJournals(local: JournalStore, remote: JournalStore): JournalStore;
//   양쪽에 있으면 updatedAt이 큰 쪽. 같으면 local(S2: 로컬 권위). 한쪽에만 있으면 그대로 채택.

// src/lib/sync/journal-remote.ts
export function pullRemoteJournal(userId): Promise<JournalStore | null>;
export function pushLocalJournal(userId, store): Promise<void>;
//   1) 로컬 전 항목 upsert (onConflict: "user_id,entry_date")
//   2) 로컬에 없는 서버 행 삭제 (S4)
```

`pushLocalJournal`은 upsert와 delete 두 번의 왕복을 쓴다. 순서는 **upsert 먼저**다. delete가 먼저면 그 사이 실패했을 때 서버에 아무것도 없는 창이 생긴다.

**로컬이 빈 경우 delete를 실행하지 않는다.** `loadJournal()`은 localStorage 파손·파싱 실패 시에도 `{}`를 반환하므로, 빈 로컬을 그대로 신뢰하면 파손 한 번이 서버 백업 전체를 지운다. 백업이 존재 이유인 기능에서 이 위험은 받아들일 수 없다.

대가는 **일기를 전부 지웠을 때(마지막 한 개 삭제 포함) 그 삭제가 즉시 전파되지 않는다**는 것이다. 다음에 아무 일기나 하나 쓰면 그때 정리된다. 알려진 한계로 남기고, 톰스톤이 필요해지는 시점(=멀티 디바이스, S1 범위 밖)에 함께 해결한다.

## 6. 오류 처리

| 상황 | 처리 |
|---|---|
| env 미설정 | 모든 원격 함수가 이미 `null`/no-op. `SyncBridge`도 즉시 반환 |
| 세션 없음 | push 시도 자체를 하지 않음 |
| pull 실패 | `syncOnLogin`이 `remote === null`이면 로컬 유지(기존 동작). 상태 `error` |
| push 실패 | `console.error` + 상태 `error`. 다음 변경/`online`에서 자동 재시도 |
| 로그인 직후 중복 push | `syncing` 플래그로 자기 자신이 유발한 notify를 무시 |
| 로그아웃 중 flush 실패 | **로그아웃을 중단**하고 `동기화되지 않은 기록이 있어 로그아웃하지 못했습니다. 네트워크 확인 후 다시 시도해 주세요.`를 보여준다. 로컬을 비우면 아직 서버에 없는 기록이 영구 소실되고, 비우지 않은 채 로그아웃하면 S5의 유출 위험이 남는다 — 어느 쪽도 조용히 감수하지 않는다 |

동기화 상태는 `"idle" | "syncing" | "ok" | "error"` + `lastSyncedAt`(localStorage `arcana.sync.lastAt`, 새로고침 후에도 표시)으로 두고, MY `AccountCard`가 한 줄로 읽는다.

## 7. 테스트

Supabase 없이 검증 가능한 부분에 유닛테스트를 집중한다(현행 vitest, 네트워크 모킹 없음).

- `mergeJournals` — 한쪽에만 존재 / 양쪽 존재 시 LWW / 동일 `updatedAt` 시 결정적 선택 / 빈 스토어.
- `local-events` — 구독·해제, 채널 격리(`journal` emit이 `store` 구독자를 깨우지 않음), 다중 구독자.
- `store.ts` — `saveStore`가 `notifyLocal("store")`를 부르는지(기존 17개 테스트는 그대로 통과해야 함).
- `journal.ts` — `setEntry`가 `notifyLocal("journal")`을 부르는지.

`SyncBridge`·원격 왕복은 유닛테스트하지 않는다. Supabase 설정 완료 후 **수동 검증 체크리스트**로 확인한다: 게스트 기록 → 로그인 → 서버 행 확인 → 새 리딩 → 2초 후 서버 반영 → 일기 작성·삭제 반영 → 로그아웃 시 로컬 비움 → 재로그인 시 복구.
