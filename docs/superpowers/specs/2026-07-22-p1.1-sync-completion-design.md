## 1. 배경

P1.0에서 스키마·클라이언트·`mergeStores`·`pullRemoteStore`/`pushLocalStore`를, P1.1에서 세션·OAuth 콜백·`syncOnLogin`을 만들었다. 그러나 실제로 데이터가 흐르지 않는다:

1. **`pushLocalStore`를 아무도 호출하지 않는다.** `syncOnLogin` 안에서 단 한 번뿐이라, 로그인 이후에 뽑은 리딩은 서버에 영영 올라가지 않는다.
2. **저널은 원격 경로 자체가 없다.** `journal_entries` 테이블은 있지만 `pullRemoteJournal`/`pushLocalJournal`이 없다.
3. **`useArcanaStore`는 마운트 시 1회만 읽는다.** `refresh`를 호출하는 곳이 없어, `AccountCard`가 로그인 병합을 끝내도 열려 있는 화면은 옛 값을 계속 보여준다.

세 결손은 개별 버그가 아니라 **"로컬 저장이 바뀌었다"는 사실을 전파할 통로가 없다**는 하나의 결손이다. 본 설계는 그 통로를 만들고 세 문제를 동시에 닫는다.

| S14 | 델타 push (2026-07-28) | push는 **서버에 아직 없다고 아는 것만** 올린다. 리딩은 앎에 없는 id만, 일기는 `updatedAt`이 다른 날짜만. 일기 정리도 **지울 날짜만 짚어** 지운다(`in`), 앎이 없을 때만 종전의 전체 나열(`not.in`)로 물러선다. 셋 다 비면 왕복 자체가 사라진다 |

| S16 | 병합 왕복 병렬화 (2026-07-28) | 리딩·일기·엔타이틀먼트는 서로 독립이므로 **함께 띄운다.** 각 갈래 안의 pull→push 순서는 그대로다. 엔타이틀먼트 pull은 `userId`를 인자로 받는다 — 예전에는 호출자가 아는 값을 두고 `auth.getUser()`로 왕복을 한 번 더 냈다 |

### S1·S2를 개정한 이유 (2026-07-28)

원문을 남겨 둔다. **이 결정 자체가 틀렸다기보다, 결정 이후에 서비스가 사용자에게
다른 약속을 하면서 문서끼리 어긋났다.**

- `src/data/legal/terms.ts` 제4조: "계정 연동: 로그인하신 경우 위 기록을 계정에
  보관하여 **여러 기기에서 이어 볼 수 있게** 합니다."
- 같은 파일 제7조: "기록을 오래 보관하고 **여러 기기에서 이어 보기를** 원하시는
  경우 로그인해 주시기 바랍니다."
- `src/data/legal/privacy.ts`: 개인정보 이용 목적에 "**여러 기기에서 같은 기록을
  이어 볼 수 있도록 하는 동기화**"가 들어 있다.

S1의 "한 번에 한 기기" 가정 아래에서는 pull이 로그인 시점 1회뿐이라, B 기기에서
남긴 기록이 이미 열려 있는 A 기기에 나타나지 않는다. 약관이 이미 게시된 이상
코드가 약속을 따라가는 편이 맞다고 보아 포그라운드 재동기화를 범위 안으로 옮겼다.

실시간 구독(Realtime)은 여전히 범위 밖이다. 탭 복귀·주기 갱신으로 충분하고,
연결을 상시로 물고 있을 만큼의 값어치가 없다.

S4(톰스톤 없음)·S4a(pull 성공 시에만 prune)는 **그대로 유지한다.** 다만 S4의 알려진
한계 — 일기를 전부 지우면 그 삭제가 즉시 전파되지 않는 것 — 는 이제 멀티 디바이스
상황에서 더 자주 드러난다. 톰스톤은 여전히 별도 과제다.

S3(LWW)은 S3a로 갈랐다. **알려진 대가:** 로그인 최초 병합에서 같은 날짜가 양쪽에
있으면 이 기기에서 게스트로 쓴 글이 **알림 없이 서버 것으로 대체된다.** 사용자가
의도한 동작이고(계정 기록이 정본), 게스트가 일기를 쓴 바로 그 날짜에 서버에도
일기가 있어야 성립하므로 드물다. 화면에 알림을 띄우려면 병합 결과를 UI까지
전달할 통로가 필요한데 지금은 그런 통로가 없다 — 필요해지면 그때 만든다.

### S7을 택한 이유

대안은 호출부에서 `recordReading()` 뒤에 push를 명시 호출하는 것이었다. diff는 작지만 (a) 새 저장 경로가 생길 때 빠뜨리면 **조용히 백업이 새고**, (b) UI 갱신은 여전히 별도 메커니즘이 필요해 결국 두 갈래가 된다. 이벤트 방식은 저장하면 반드시 흐르므로 P2에서 사주 리딩 저장 경로가 추가돼도 누락이 구조적으로 불가능하다.

## 3. 아키텍처

새로 생기는 조각은 3개다.

```
src/lib/local-events.ts     변경 이벤트 채널 (~25줄, 의존성 없음)
src/components/SyncBridge   layout에 1개. 세션 관찰 + 디바운스 push + 상태 노출
src/lib/sync/journal-remote.ts  저널 pull/push
```

2026-07-28 추가: `src/lib/sync/server-knowledge.ts` — 서버에 무엇이 있는지에 대한
이 세션의 앎(S14·S15). pull이 채우고 push가 갱신한다. 메모리에만 있고 다른 모듈을
import하지 않는다.

의존 방향은 한 방향으로 유지한다:

```
store.ts / journal.ts  ──emit──▶  local-events.ts  ◀──subscribe──  useArcanaStore / useJournal
                                        ▲
                                        └──subscribe──  SyncBridge ──▶ sync/*  ──▶ supabase/*
```

`store.ts`·`journal.ts`는 **Supabase를 import하지 않는다.** 로컬 우선 원칙(P1.0 Global Constraints)이 그대로 유지되고, 두 파일의 유닛테스트도 네트워크와 무관하게 남는다.

### 3.1 `local-events.ts`

```ts
export type LocalChannel = "store" | "journal";
export function subscribeLocal(ch: LocalChannel, fn: () => void): () => void;
export function notifyLocal(ch: LocalChannel): void;
```

채널을 나누는 이유는 일기 저장이 도감 화면을 리렌더시키지 않게 하기 위함이다. SSR 안전(모듈 스코프 `Map`, 브라우저 전용 API 없음).

### 3.2 emit 지점

`store.ts`의 `saveStore`, `journal.ts`의 `saveJournal` **내부** 끝에서 emit한다. 두 함수는 이미 모든 쓰기(`recordReading`, `setLocalStore`, `setEntry`)가 지나는 단일 통로이므로, 여기 한 곳만 잡으면 새는 경로가 없다.

### 3.3 구독 지점

- `useArcanaStore` / `useJournal`: 마운트 시 해당 채널을 구독해 `refresh`를 건다. 기존 `refresh` 반환값은 유지(호환).
- `SyncBridge`: 두 채널을 모두 구독한다.

### 3.4 `SyncBridge`

`layout.tsx`의 `<body>`에 `<NoPinchZoom />` 옆에 놓는 클라이언트 컴포넌트. UI를 렌더하지 않는다(`null`).

책임:
1. `useSession()`으로 `user: null → {id}` 전이를 감지해 `syncOnLogin(id)` + `syncJournalOnLogin(id)` 실행. (지금 `AccountCard`가 갖고 있는 이 로직을 여기로 **옮긴다** — MY 화면을 열어야만 병합되는 현재 동작은 버그다.)
2. 변경 이벤트를 받아 **2초 디바운스** 후 로그인 상태면 push.
3. `window` `online` 이벤트에 push를 건다(오프라인 복귀 복구).
4. 동기화 상태를 노출한다.

## 4. 데이터 흐름 시나리오

### 게스트 (env 없음 또는 미로그인)
`recordReading()` → `saveStore()` → `notifyLocal("store")` → 화면 갱신. `SyncBridge`는 세션이 없어 무시. **현행과 동일하며 네트워크 호출이 없다.**

### 첫 로그인 (게스트 기록 보유)
```
OAuth → /auth/callback → 세션 확립
  → SyncBridge가 전이 감지
  → syncOnLogin(id):        pull → mergeStores → setLocalStore → push
  → syncJournalOnLogin(id): pullRemoteJournal → mergeJournals(LWW) → setLocalJournal → push
       ↑ setLocalStore/setLocalJournal이 notify를 쏘므로 열려 있는 모든 화면이 병합 결과로 갱신
```

### 로그인 상태에서 저장
`recordReading()` / `setEntry()` → notify → ①화면 갱신 ②`SyncBridge` 디바운스 2초 → push.

### 오프라인·실패
push 실패 → 상태 `error` → MY에 `동기화 대기 중`. 로컬은 이미 저장돼 앱은 정상 동작. `online` 복귀 또는 다음 저장 시 전체 멱등 upsert로 밀린 분까지 복구.

### 로그아웃
```
signOutAndClear():
  대기 중 push flush(3초 타임아웃, 실패해도 계속)
    → localStorage 비움(리딩·일기·arcana.sync.lastAt) → 동기화 상태 idle로 리셋
    → notify → 화면 리셋 → supabase.auth.signOut()
```
`lastAt`까지 지우는 이유는 S5와 같다 — 지우지 않으면 다음 계정이 아직 아무것도 올리지 않았는데 이전 사용자의 `마지막 동기화 HH:MM`을 본다.
flush 성공 여부와 무관하게 로그아웃은 완주한다(S5a). 재로그인 시 pull로 복구된다.

## 5. 저널 원격 계층

`journal_entries` 스키마: `(user_id, entry_date)` PK, `body`, `updated_at`.

```ts
// src/lib/sync/merge.ts (순수 · 테스트 대상)
export function mergeJournals(local: JournalStore, remote: JournalStore): JournalStore;
//   양쪽에 있으면 updatedAt이 큰 쪽. 같으면 local(S2: 로컬 권위). 한쪽에만 있으면 그대로 채택.

// src/lib/sync/outcome.ts
export type SyncOutcome = "ok" | "failed" | "skipped";           // S6b
export type PullResult<T> = { outcome: "ok"; data: T } | { outcome: "failed" | "skipped" };

// src/lib/sync/journal-remote.ts
export function pullRemoteJournal(userId): Promise<PullResult<JournalStore>>;
export function pushLocalJournal(userId, store, options: { prune: boolean }): Promise<SyncOutcome>;
//   1) 로컬 전 항목 upsert (onConflict: "user_id,entry_date")
//   2) options.prune일 때만 로컬에 없는 서버 행 삭제 (S4·S4a)
```

`prune`은 **선택 인자가 아니라 필수**다. 기본값을 두면 호출부가 실수로 삭제를 켤 수 있고, 그 실수의 대가가 서버 데이터 소실이다.

`pushLocalJournal`은 upsert와 delete 두 번의 왕복을 쓴다. 순서는 **upsert 먼저**다. delete가 먼저면 그 사이 실패했을 때 서버에 아무것도 없는 창이 생긴다.

**로컬이 빈 경우 delete를 실행하지 않는다.** `loadJournal()`은 localStorage 파손·파싱 실패 시에도 `{}`를 반환하므로, 빈 로컬을 그대로 신뢰하면 파손 한 번이 서버 백업 전체를 지운다. 백업이 존재 이유인 기능에서 이 위험은 받아들일 수 없다.

대가는 **일기를 전부 지웠을 때(마지막 한 개 삭제 포함) 그 삭제가 즉시 전파되지 않는다**는 것이다. 다음에 아무 일기나 하나 쓰면 그때 정리된다. 알려진 한계로 남기고, 톰스톤이 필요해지는 시점(=멀티 디바이스, S1 범위 밖)에 함께 해결한다.

## 6. 오류 처리

| 상황 | 처리 |
|---|---|
| env 미설정 | 모든 원격 함수가 `"skipped"`를 반환한다. `SyncBridge`도 즉시 반환 |
| 세션 없음 | push 시도 자체를 하지 않음 |
| pull 실패 | 로컬을 그대로 두고 상태 `error`. **그리고 그 세션 동안 저널 prune을 끈다**(S4a) |
| push 실패 | 원격 함수가 `console.error` 후 `"failed"`를 **반환**한다(던지지 않는다, S6b). 호출부가 그 값으로 상태 `error`를 세운다. 다음 변경/`online`에서 자동 재시도 |
| 로그인 직후 중복 push | 진행 중 작업 수(`inFlight`)로 자기 자신이 유발한 notify를 무시하되, **그 사이 들어온 사용자 저장은 `dirty`로 기억해 작업이 끝나면 다시 예약**한다(S6a). 불리언 플래그가 아니라 카운터인 이유는, 겹친 두 작업 중 먼저 끝난 쪽이 나머지의 플래그까지 내려버리기 때문이다 |
| 로그아웃과 병합의 경합 | `epoch` 카운터를 둔다. 진행 중이던 병합은 로컬에 쓰기 직전 자기 epoch가 유효한지 확인한다. 이게 없으면 로그아웃이 비운 로컬을 뒤늦게 끝난 병합이 되살려 S5가 깨진다. **epoch는 `setSyncUser`뿐 아니라 `flushPendingSync`가 반환할 때도 올린다** — 로그아웃 순서가 `flush → 로컬 비움 → signOut → (auth 이벤트) → setSyncUser(null)`이라, `setSyncUser`에서만 올리면 "비움"과 "setSyncUser" 사이에 끝난 병합이 그대로 로컬을 되살린다 |
| 로그아웃 중 flush 실패 | **로그아웃을 그대로 진행한다**(S5a). flush에 3초 타임아웃을 두어 네트워크가 죽어 있어도 로그아웃이 매달리지 않게 하고, 실패해도 로컬을 비우고 세션을 끊는다. 마지막 성공 push 이후의 델타는 유실된다 — S5(유출 방지)와 S5a(통제권)를 유실보다 우선한 결과다 |

동기화 상태는 `"idle" | "syncing" | "ok" | "error"` + `lastSyncedAt`(localStorage `arcana.sync.lastAt`, 새로고침 후에도 표시)으로 두고, MY `AccountCard`가 한 줄로 읽는다.

## 7. 테스트

Supabase 없이 검증 가능한 부분에 유닛테스트를 집중한다(현행 vitest, 네트워크 모킹 없음).

- `mergeJournals` — 한쪽에만 존재 / 양쪽 존재 시 LWW / 동일 `updatedAt` 시 결정적 선택 / 빈 스토어.
- `local-events` — 구독·해제, 채널 격리(`journal` emit이 `store` 구독자를 깨우지 않음), 다중 구독자.
- `store.ts` — `saveStore`가 `notifyLocal("store")`를 부르는지(기존 17개 테스트는 그대로 통과해야 함).
- `journal.ts` — `setEntry`가 `notifyLocal("journal")`을 부르는지.
- **`pusher.ts`** — 원격 모듈을 `vi.mock`하고 가짜 타이머로: 게스트일 때 아무것도 예약하지 않음(S8), 디바운스 합치기, **진행 중 push 사이에 들어온 저장이 유실되지 않음**(S6a), push가 매달려도 `flushPendingSync`가 타임아웃 안에 반환, `"failed"` 반환 시 상태가 `error`(S6b), `pullOk: false`면 `prune: false`로 push(S4a).
- `journalPruneFilter` — 손으로 조립하는 PostgREST 필터 문자열의 인용 부호.

`pusher.ts`는 React·DOM 의존이 없어 node 환경에서 그대로 테스트된다. 애초에 순환 참조 때문에 컴포넌트에서 떼어낸 모듈인데, 결과적으로 **결함이 몰리는 곳**이기도 하므로 테스트 대상에서 빼면 안 된다.
