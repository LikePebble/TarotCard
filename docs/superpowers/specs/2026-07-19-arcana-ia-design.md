# 아르카나 IA 구조 개선 설계 (redesign/arcana)

- 작성일: 2026-07-19
- 브랜치: `redesign/arcana`
- 범위: **서비스 정보구조(IA) / 화면 흐름 / 게스트·계정 경계**의 재설계 청사진.
  각 영역(계정, 사주 엔진, 덱 스토어, 일별 기록)의 상세 구현 스펙은 본 문서를 상위 기준으로 삼아 개별 스펙으로 분리한다.

## 1. 배경과 문제 정의

현재 아르카나는 2탭(`리딩`·`컬렉션`) 구조의 Next.js 앱이며, 상태는 전부 브라우저 `localStorage`에 있다(서버·계정·인증 없음).

핵심 결손:

1. **MY / 계정 영역 부재** — 일별 기록·일기, 덱 관리, 계정 관리가 들어갈 자리가 없다.
2. **진입 분기 부재** — 첫 화면에 "로그인 / 둘러보기" 갈림이 없다.
3. **덱 상품화 미구현** — `decks.ts`에 `price?`·`active` 필드만 있고, 덱별 설명·잠금·구매가 없다.
4. **"컬렉션" 용어 과부하** — ①78장 수집 도감과 ②덱(스킨)이 한 화면에 뭉개져 있다.
5. **리딩 결과가 독립 화면이 아님** — `reading/draw`(759줄)에 셔플·선택·해석·공유가 묻혀 있어, 일기 첨부·"다시 보기"가 불가능하다.
6. **사주 × 타로라는 새 서비스 유형의 토대 부재** — 계정이 필요한 근본 이유. 생년월일시(민감정보) 개인화가 들어갈 구조가 없다.

## 3. 용어 정의 (Ubiquitous Language)

- **덱(Deck)**: 78장 카드의 아트 스타일 한 벌. 상품 단위. 무료/유료, 소유(entitlement) 개념을 가진다. 예: 클래식, 월하비원.
- **도감(Catalog)**: 특정 덱에서 사용자가 리딩으로 만난 카드의 수집 진행도(`n/78`). 덱별로 독립적으로 채워진다.
- **리딩(Reading)**: 한 번의 점(占) 세션. 유형(컨테이너)·질문 카테고리·선택 카드·해석·스냅샷을 가지는 독립 엔티티.
- **컨테이너/리딩 유형(Reading Type)**: `ONE_CARD`(오늘의 타로), `THREE_CARD_PPF`(과거·현재·미래). 확장 가능한 데이터 테이블.
- **사주 셔플(사용자 노출명)**: 출생 사주와 오늘의 흐름으로 카드 배열을 개인화하는 기능. 내부명 `사주 운명 셔플`. ("운명 해시"는 기술 내부명으로만, 사용자 노출 금지.)
- **명식 토큰(natal token)**: 생년월일 원문이 아니라 표준화된 명식(사주 네 기둥)을 서버 시크릿으로 HMAC 처리한 값.

## 5. 게스트 / 계정 경계 (권한 매트릭스)

| 기능 | 게스트 | 로그인 |
|---|---|---|
| 타로 리딩 (사주 미반영) | ✅ 로컬 | ✅ |
| **사주 반영 리딩** | ❌ | ✅ (프로필 입력 시, **서버 생성**) |
| 도감 수집 | ✅ 기기 로컬 | ✅ 서버 동기화 |
| 일별 기록 · 일기 | ⚠️ 로컬 임시 | ✅ 안전 보관 |
| 덱 구매 | ❌ (로그인 유도) | ✅ |
| 리롤 방지 강제력 | 약함(클라 한정) | **강함(서버 커밋)** |

- **전환(게스트 → 로그인)**: 로컬 도감·일기·리딩 기록을 계정으로 **병합(merge)**. 병합 규칙(중복 처리·우선순위)은 계정 스펙에서 상세화.
- **로그인 유도 시점**: (a) 덱 구매, (b) 사주 반영 활성, (c) 기기 간 보관/백업. 강제 벽이 아니라 순간(moment) 유도.
- **등급(entitlement)은 로그인과 직교하는 별개 축** (D15): `무료` / `ad_free`. `ad_free`는 광고 제거 + 오늘의 타로 3슬롯을 부여하며, 광고제거 상품 또는 유료 덱 구매로 획득. 광고 노출은 무료 등급 한정.

## 6. 리딩 엔진 재구조

### 6.1 결과의 독립 엔티티화 (P0 핵심)

- `reading/draw` 단일 파일에서 **선택 로직**과 **결과 표현**을 분리한다.
- 리딩 완료 시 결과는 `/reading/[id]`로 접근 가능한 독립 엔티티가 된다.
- 결과 레코드 스냅샷(당시 값 동결): `reading_id`, `created_at`, `local_date`, `주차`, `type`, `question_category`, `deckId`, 선택 카드 목록, **카드 방향(정/역)**, `saju_rule_version`, `shuffle_version`.
  - 사주 프로필이 나중에 바뀌어도 **과거 리딩은 불변**.

### 6.2 리딩 유형을 데이터로

- `ONE_CARD` / `THREE_CARD_PPF`를 하드코딩이 아닌 유형 테이블로 정의. 각 유형이 선언:
  - 뽑는 장수, 포지션 의미(과거/현재/미래), **케이던스**(일/주), 질문 카테고리 집합.
- 향후 사주 단독·신규 스프레드가 같은 컨테이너 규약으로 확장된다.

### 6.3 사주 셔플 (D3~D5, 서버 권위)

파이프라인(사용자 문서 최종 권장 구조 채택):

```text
보안 난수로 78장 기본 셔플
→ 사주 + 현재 운기로 덱 컷(위치·방향)
→ 뒷면 펼침
→ 사용자가 1장(오늘) 또는 3장(PPF, 같은 덱에서 순서대로) 직접 선택
→ 질문 카테고리 맥락으로 해석 (+ 명식 렌즈)
```

- **명식은 원문 해시 금지.** `natal_token = HMAC-SHA256(server_secret, canonical_saju)`.
- **운기 스냅샷은 리딩 생성 순간 1회 계산·고정** (초/밀리초 반영 금지).
- **질문 원문은 셔플 시드에 넣지 않음** (카테고리 코드만). 원문은 해석 단계에서만 사용.
- PPF는 **한 번의 셔플·한 번의 사주 컷**으로 만든 하나의 배열에서 세 장 선택(세 장 개별 셔플 금지). 선택 순서 = 과거·현재·미래 고정, 선택 카드는 덱에서 제거.
- 미래 카드는 "확정된 미래"가 아니라 "현재 흐름이 이어질 때의 가능성"으로 표현.

### 6.4 MVP 경계 (과설계 방지)

- **v1 필수(5):** HMAC 명식 토큰 · 시드 고정(스냅샷) 셔플 · 서버 커밋 리딩 · 컷 의례 연출 · 해석의 명식 인용.
- **후속:** HKDF 이중 스트림(순서/방향 분리), 3영역 UI(방안 B), A/B 테스트 인프라, 정교한 월주+일주 이중 스냅샷.

## 7. 케이던스 & 리롤 방지 (D11~D14)

| 컨테이너 | 케이던스 | period key | 서비스 언어 |
|---|---|---|---|
| 오늘의 타로 | **카테고리당 1회 / 일**, 하루 총 슬롯 = 무료 1 · `ad_free` 3 | `local_date` + `question_category` | "하루 한 장" / (프리미엄) "오늘, 세 가지 질문" |
| 과거·현재·미래 | 1회 / 주 (등급 무관) | ISO 주차 `YYYY-Www` | ~~"이번 주의 흐름"~~ → **"이번 주의 운명"** (2026-07-28 개정) |

- **오늘의 타로 슬롯 규칙 (D14·D15):**
  - 각 질문 카테고리는 하루 1회. 뽑은 카테고리는 그날 **잠금** → 유형/카테고리 카드가 "결과 보기"로 전환.
  - 하루 총 소비 가능 슬롯: 무료 1개, `ad_free` 보유 3개. **3개는 반드시 서로 다른 카테고리**(같은 테마 재뽑기 = 리롤이므로 불가).
  - "3회"는 *다시 뽑기*가 아니라 *더 많은 주제를 묻기*. 카피에서 리롤로 지칭 금지.
- **상태 모델** (사용자 × 컨테이너 × 카테고리 × 현재 주기):
  - `available` → 리딩 시작 가능 (또는 남은 슬롯 있음)
  - `completed` → 해당 카테고리 카드가 **"결과 보기"**로 전환, `/reading/[id]`로 이동
  - `slot_exhausted` → (무료) "오늘의 흐름은 이미 받으셨어요" · (프리미엄) 3슬롯 소진 시 동일
  - PPF `locked` → *"이번 주의 운명은 이미 받으셨습니다."* (2026-07-28 개정, 원문은 "이번 주의 흐름은 이미 받으셨어요")
- **리롤 방지 4중:**
  1. 케이던스/슬롯 캡(주 장치) — 카테고리 잠금으로 같은 질문 재뽑기 불가, 취소 후 재리딩 불가.
  2. 서버 커밋 — 질문 확정 시 `reading_id` 발급·저장. 새로고침/뒤로가기/취소는 **진행 중 같은 리딩으로 복귀**. 최종 공개 후에만 슬롯 소비 확정.
  3. 결정론 시드 — 진행 중 리딩의 카드 배열이 재접속에도 동일.
  4. 소프트 문구 — 결과 재접속 시 기존 카드 그대로, 단정적 표현 회피.

## 8. 데이터 모델 진화

- **게스트(localStorage):** 현행 유지 + `collection`을 **덱별 구조**로 확장(현재 전역 slug 맵 → `{ [deckId]: { [slug]: entry } }`). 리딩 레코드에 `deckId`·방향·스냅샷 추가.
- **계정(서버):** `user`, `saju_profile`(canonical 명식 + natal_token, 원문 최소보관/암호화), `readings`(스냅샷 불변), `journal`(date → entries), `entitlements`(소유 덱, `ad_free`, 오늘의 타로 슬롯 수), `collection`(덱별), `settings`.
- **오늘의 타로 슬롯 상태:** `(user, local_date)` 기준 소비 슬롯/사용 카테고리 집합을 서버가 권위 보유(무료 1·`ad_free` 3). 게스트는 로컬 근사(강제력 약함).
- **백엔드 스택**: 미정 — P1 진입 전 별도 결정(인증·DB·서버 시크릿·보안난수·결제 PG 요건 포함).

## 9. 단계적 구현 (Phasing)

| Phase | 내용 | 서버 필요 | 비고 |
|---|---|---|---|
| **P0** | 결과 화면 독립(`/reading/[id]`) + 덱별 도감 리팩터 + 리딩 유형 데이터화 + 케이던스 상태(로컬) | ❌ | 즉시 가치, 후속의 토대 |
| **P1** | 계정(카카오·구글) + 백엔드 + MY 허브 + 일별 기록·일기 + 게스트→계정 병합 | ✅ | 백엔드 스택 결정 선행 |
| **P2** | 사주 프로필 + 서버 권위 사주 리딩 + 리롤 방지 서버화 + 사주 DB(6tail+한국레이어) + 해석 명식 인용 | ✅ | D3~D6 |
| **P3** | 덱 스토어 결제 + 엔타이틀먼트(`ad_free`) + 광고 노출/제거 + 오늘의 타로 3슬롯 해금 + 구매 복원 + 법적 고지(약관·개인정보·결제) | ✅ | D7·D15 |

## 10. 카피 가이드 (금지/권장)

- **권장:** "사주와 오늘의 흐름으로 카드의 배열을 만들었습니다. 그중 어떤 카드를 만날지는 당신의 선택에 달려 있습니다."
- **결과 고지:** "이 결과는 미래를 확정하는 판정이 아니라, 사주와 타로의 상징으로 현재 상황과 선택을 다른 관점에서 바라보기 위한 가이드입니다."
- **금지:** "사주가 당신의 카드를 골랐다 / 운명이 이 카드로 결정됐다 / 미래에 실제로 일어날 일을 정확히 보여준다 / 적중 알고리즘".
- **"운명"이라는 낱말 자체는 금지가 아니다** (2026-07-28 명시). 금지되는 것은 *카드가
  운명을 정한다*는 주장이지 명사가 아니다. 사주·타로에서 관용적으로 쓰는 말이므로
  "이번 주의 운명" 같은 서비스 언어로는 쓴다. 예측하지 않는다는 고지는 이용약관
  제5조가 맡는다. 과거에 이 줄을 근거로 "운명 → 흐름" 치환이 있었으나 되돌렸다 —
  1장이 이미 "오늘의 흐름"이라 두 리딩이 언어로 구분되지 않았다.
