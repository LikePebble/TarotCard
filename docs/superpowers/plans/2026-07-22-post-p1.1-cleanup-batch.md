### Task 1: `readings` PK를 `(user_id, id)` 복합키로

**왜 지금인가.** `readings.id`가 전역 PK라 서로 다른 사용자가 같은 id를 만들면 충돌한다. 도달 경로가 실재한다 — `migrateReading`([`src/lib/store.ts:47`](../../../src/lib/store.ts))이 레거시 v1 리딩의 id를 `` `${at}-${i}` ``로 만드는데, `at`이 없거나 문자열이 아니면 `new Date(0)`으로 떨어져 **사용자와 무관하게 `1970-01-01T00:00:00.000Z-0`이 나온다.** 두 번째 사용자의 upsert는 남의 행을 건드리게 되고 RLS(`auth.uid() = user_id`)에 막혀 push가 영구 실패한다.

**아직 마이그레이션을 실행하지 않았기 때문에 스키마 수정이 공짜다.** 실행 후였다면 데이터 마이그레이션이 따라붙는다. 이 태스크의 유효기간은 Supabase 설정 시점까지다.

**클라이언트 id 생성은 건드리지 않는다.** 지금의 결정적 id는 같은 레거시 스토어를 두 기기에서 열었을 때 같은 값을 내어 서버에서 저절로 합쳐진다. 랜덤 uuid로 바꾸면 그 성질이 깨지는데, `loadStore`가 마이그레이션 결과를 **다시 저장하지 않아**([`src/lib/store.ts:89`](../../../src/lib/store.ts)) 매 로드마다 새 id가 생겨 서버에 중복 행이 쌓인다. 문제는 id 생성이 아니라 PK의 범위다.

**형제 테이블과 맞추는 변경이기도 하다.** `journal_entries`는 이미 `primary key (user_id, entry_date)`에 `onConflict: "user_id,entry_date"`를 쓴다. `readings`만 혼자 전역 PK다.

- [x] **1a.** `supabase/migrations/0001_p1_foundation.sql`의 `readings` 정의에서 `id text primary key`를 `id text not null`로 바꾸고, 테이블 끝에 `primary key (user_id, id)`를 추가한다. 주석은 유지하되 "전역"이 아니라 "사용자 범위 멱등키"임이 드러나게 다듬는다.
- [x] **1b.** [`src/lib/sync/remote.ts:88`](../../../src/lib/sync/remote.ts)의 `.upsert(rows, { onConflict: "id" })`를 `{ onConflict: "user_id,id" }`로 바꾼다.
- [x] **1c.** `npx tsc --noEmit` · `npm test` 통과 확인.

**검증의 한계:** 원격 왕복은 유닛테스트하지 않기로 되어 있다(P1.1 설계 §테스트). 실동작 확인은 Supabase 설정 후 수동 검증 체크리스트에서 이루어진다. 이 태스크에서는 스키마와 `onConflict` 문자열이 서로 맞는지를 눈으로 확인하는 것이 전부다. **둘이 어긋나면 런타임에서야 드러난다** — 반드시 같이 고칠 것.

### Task 2: MY에서 덱 관리 제거

**왜.** 기본 덱은 컬렉션 두 곳에서 이미 설정할 수 있다 — [`src/app/collection/page.tsx:56`](../../../src/app/collection/page.tsx)과 [`src/app/collection/[deckId]/page.tsx:82`](../../../src/app/collection/[deckId]/page.tsx). `/my/decks`는 세 번째 지점이고 하는 일이 같다.

**이것은 결정 C6의 번복이다.** [`docs/superpowers/specs/2026-07-22-collection-ia-design.md`](../specs/2026-07-22-collection-ia-design.md)의 C6은 설정 지점을 의도적으로 **두 곳**(컬렉션과 MY)으로 두었다. 실물을 놓고 보니 MY 쪽이 값을 더하지 않아 되돌린다. 스펙 §4 사이트맵의 `/my/decks`("디폴트 덱 설정, 소유 덱")에서 앞은 컬렉션이 가져갔고, 뒤(소유 덱)는 P3 구매 기능이라 그때 `/my/purchases`와 함께 다시 판단한다.

- [x] **2a.** [`src/app/my/page.tsx:77-93`](../../../src/app/my/page.tsx)의 `/my/decks` 진입 `<Link>` 블록을 삭제한다. 남는 카드 순서는 일별 기록 → 사주 프로필(준비 중) → `AccountCard`.

- [x] **2d.** C6 번복을 설계 문서에 반영한다 — 위 design.md의 C6 행에 번복 사실과 날짜를 한 줄로 남긴다. 원문을 지우지 말 것. 결정이 바뀐 기록이 결정 자체보다 유용하다.

### Task 3: 결과 화면에 그날 일기 진입점

**무엇을 푸는가.** 지금 링크는 한 방향뿐이다 — [`src/app/my/journal/[date]/page.tsx:131`](../../../src/app/my/journal/[date]/page.tsx)에서 리딩으로 갈 수는 있어도, 결과를 보다가 일기로 가려면 MY → 일별 기록 → 달력에서 날짜 찾기까지 네 번 이동해야 한다.

**뽑기 직후 화면([`src/app/reading/draw/page.tsx`](../../../src/app/reading/draw/page.tsx))에는 넣지 않는다.** 일기는 그날 카드가 실제로 어떻게 투영되었는지를 적는 **회고**이므로, 뽑는 시점에는 쓸 내용이 아직 없다. 반대로 `/reading/[id]`는 "다시 보기" 화면이고, 그 화면을 여는 사람은 이미 하루를 지나 보낸 사람이다. 진입점은 여기에만 둔다.

- [x] **3a.** [`src/app/reading/[id]/page.tsx`](../../../src/app/reading/[id]/page.tsx)에서 `useJournal`을 가져와 그날 일기 유무를 읽는다.
- [x] **3b.** SSR 게이트를 저널까지 넓힌다. 현재 `store === null`일 때 빈 화면으로 빠지는데(같은 파일 39행), 여기에 저널도 포함시킨다. 그러지 않으면 라벨이 "쓰기"에서 "보기"로 깜빡인다.
- [x] **3c.** `OneCardResult`·`ThreeCardResult`의 `actions`에 `btn btn-ghost` 링크를 추가한다. 목적지는 두 경우 모두 `/my/journal/${reading.localDate}`, 라벨만 갈린다:
  - 일기 없음 → `이날의 일기 쓰기`
  - 일기 있음 → `이날의 일기 보기`
- [x] **3d.** `npx tsc --noEmit` · `npm test` 통과 확인.

**테스트를 새로 만들지 않는 이유:** 순수 로직이 없다. 조건부 문자열 하나뿐이라 유닛테스트가 확인할 것이 없다. 브라우저 확인으로 대신한다.
